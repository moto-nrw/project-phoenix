# Frontend performance guardrails

Read before changing bundle baselines, shell rendering, or performance tooling.
Paths below are relative to `frontend/` except `.github/` and `docs/`.

## Ratchets and evidence (#2939)

- **Two bundle gates (#5231, decision C)** (`lint / frontend-build`): PR growth per existing route must not exceed `max(10 KiB, round(merge-base bytes × 0.02))`. Absolute per-route ceilings remain independently reviewed policy in `scripts/perf/bundle-budgets/<portal>/<resource>.json`. A newly exceeded ceiling fails. Already exceeded on the merge-base: PR warning in the job summary/annotation, not attribution to an unrelated PR; the PR's own delta is still blocking. Development's full nightly run has no PR exception and fails on every absolute excess. This keeps cumulative growth visible without baseline-drift failures.
- **Exact comparison**: CI checks out the PR head, not GitHub's synthetic merge, and computes `git merge-base HEAD <event base SHA>`. Both trees compile cold in the same job with the same Node/platform/environment and parser; each installs its own frozen lockfile. The base is a disposable Git archive, removed even on failure. No cross-run/fork artifact grants a pass and no token is passed to the base build. Missing requested measurements, malformed analysis or stale source/configuration fail closed. Both measurements and their base identity are archived for 14 days. There is no age-dependent artifact lookup or fallback to historical approved references.
- **Policy ownership**: frontend maintainers review new routes and budget changes with measurement evidence and a reason in the PR. Existing fixed ceilings remain unchanged by #5231; observations never approve increases (`--update` is rejected). Removed routes and reductions pass. A reduction is protected by the next PR's new merge-base automatically; obsolete budget entries may be removed with the owning feature. New routes have no old delta but require an explicit absolute budget. Shared client code is included in each affected route, not summed as a fictitious total bundle.
- **Local reproduction** (from `frontend/`, inside Devbox, with the normal local performance environment): commit frontend sources, then run `node scripts/perf/bundle-measurement.mjs --prepare-ci "$(git merge-base HEAD origin/development)"`, `node scripts/perf/bundle-base.mjs`, and `pnpm run perf:bundle-ratchet`. This is the same cold two-tree comparison as CI. Local results are platform-specific and must not replace Linux budget evidence. Without a prepared base, `perf:bundle-ratchet` checks only absolute policy, as on nightly. The extra base analysis/install is intentional: missing observations cannot silently disable the PR gate.
- **Cold analysis and regular build**: both remain required. Chunk splits depend on Turbopack's incremental cache, so head analysis parks/restores that cache and compiles cold. `--skip-analyze` accepts only diagnostics matching the committed source/configuration. The ordinary `next build` remains because the experimental analyzer is not proved equivalent for all type/route/build validations. Versioned observations remain separate from approved budgets.

- **Render budget** (Vitest, blocking): `expectIdleRenderBudget` from `src/test/render-budget.tsx` counts `<Profiler>` commits over 5 s of fake-timer idle and caps them at 20; `mobile-bottom-nav.test.tsx` and `sidebar.test.tsx` use it. A new effect loop in the shell trips this regardless of runner speed. Keep the cap; fix the loop. Reuse the helper for any new always-mounted component.
- **Nightly counters** (`.github/workflows/perf-nightly.yml`, non-blocking): runs `pnpm run perf:trace` and `pnpm run perf:render` against a seeded backend on weeknights and via `workflow_dispatch`; the report lands in the job summary and as a 30-day artifact. Compare counters (requests per screen, duplicates, longest chain, renders per interaction) with `docs/perf/frontend-baseline-2026.md`; runner timings are not comparable across machines. Timing-based numbers (LCP, Lighthouse) are deliberately not gates.
