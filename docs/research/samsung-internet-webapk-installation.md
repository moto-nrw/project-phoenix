# Samsung Internet, WebAPK installation, and the Play Protect warning

**Researched:** 2026-08-26\
**Scope:** The Play Protect message “This app was built for an older version of Android and does not include the latest privacy protections” seen while installing the moto parents PWA from Samsung Internet. Primary sources are used for platform claims. The open Samsung support issue is explicitly treated as an unconfirmed field report.

## Conclusion

Redirecting affected Samsung Internet users to Chrome is a **reasonable immediate workaround for an installed app experience**, but it is not a fix that moto controls and it is not guaranteed forever.

For the specific warning shown, the stronger product options are:

1. **If an app icon/standalone window is required now:** detect `SamsungBrowser`, do not invoke moto's captured install prompt, and show instructions plus a user-tapped “In Chrome öffnen” link. Chrome uses its own WebAPK pipeline, separate from Samsung's. The exact Samsung support report says the same PWA installed without warning through Chrome on the same device. This is evidence for the workaround, not a vendor-confirmed root cause. ([web.dev installation architecture](https://web.dev/learn/pwa/installation), [SamsungInternet/support #123](https://github.com/SamsungInternet/support/issues/123))
2. **If notifications are the actual requirement:** allow Web Push directly in Samsung Internet without requiring installation. Samsung documents that subscribed users receive notifications whether the page is running or not. This avoids the failing APK path entirely. ([Samsung Web Development Guide](https://developer.samsung.com/internet/android/web-developer-guide.html#Web_Push))
3. **If moto needs a durable Android package under its own control:** publish a Trusted Web Activity (TWA). That gives moto control over the Android wrapper and its target SDK, but creates an Android/Play Store release surface that must be signed, verified, tested, updated, and kept policy-compliant. ([Android TWA overview](https://developer.android.com/develop/ui/views/layout/webapps/trusted-web-activities), [Chrome TWA quick start](https://developer.chrome.com/docs/android/trusted-web-activity/quick-start))

## 1. What the warning establishes

Google documents this exact text as the **Android App Compatibility Too Low** Play Protect warning. It is shown when an APK's `targetSdkVersion` is more than two API levels below the device's Android API level. It does not, by itself, establish that Google detected malware. ([Google Play Protect warning guidance](https://developers.google.com/android/play-protect/warning-dev-guidance#android_app_compatibility_too_low_warning))

The warning therefore establishes that an APK was being installed and that Play Protect considered its target API too old for the device. It does **not** by itself identify which minting service produced that APK. The screenshot plus the install flow through Samsung Internet make Samsung's WebAPK path the leading explanation, but inspecting the generated package on the affected device is required to prove its package metadata and exact `targetSdkVersion`.

An open issue in Samsung's official support repository reports the same warning for multiple PWAs installed from Samsung Internet and says Chrome succeeds on the same device. No Samsung maintainer has confirmed the issue or its proposed root cause. The issue's statement that Android 14 warns for every target below API 34 is also too broad: Google's rule is “more than two versions lower,” so Android 14/API 34 warns below API 32. Treat the issue as reproduction evidence, not authoritative diagnosis. ([SamsungInternet/support #123](https://github.com/SamsungInternet/support/issues/123), [Google warning threshold](https://developers.google.com/android/play-protect/warning-dev-guidance#android_app_compatibility_too_low_warning))

## 2. Who controls a WebAPK's target SDK

A WebAPK is created and signed by a provider trusted by the browser/device. Google documents distinct trusted-provider paths: Chrome with Google Mobile Services uses the Google/Play Services path; Samsung Internet on Samsung devices uses Samsung's path. The PWA developer does not build or sign the package. ([web.dev: WebAPKs](https://web.dev/learn/pwa/installation#webapks))

Chromium's own architecture confirms that Chrome asks a specialized minting server to generate the APK. Its source says the WebAPK shell is generated by the Chrome server and is not compiled into Chrome. ([Chromium Android web-app architecture](https://chromium.googlesource.com/chromium/src/+/79eb5783e63721b527d40d3ca16d1455af223617/components/webapps/docs/projects/al-site-settings/webapp_android_architecture.md#Installation-Systems), [Chromium WebAPK README](https://chromium.googlesource.com/chromium/src/+/refs/heads/main/chrome/android/webapk/README.md))

The site supplies web-app metadata such as name, icon, start URL, scope, and colors. The current W3C manifest specification has no Android `targetSdkVersion` member. ([W3C Web Application Manifest](https://www.w3.org/TR/appmanifest/#web-application-manifest))

Chromium makes the boundary explicit: fields that cannot be customized per site are filled before the manifest template is uploaded to the minting server. `targetSdkVersion` is in that fixed portion. Therefore moto cannot raise it through `site.webmanifest`, headers, the service worker, or Next.js configuration. ([Chromium WebAPK AndroidManifest template](https://chromium.googlesource.com/chromium/src/+/refs/heads/main/chrome/android/webapk/shell_apk/AndroidManifest.xml))

## 3. Does installing through Chrome avoid Samsung's stale wrapper?

It avoids **Samsung's minting path**. Chrome requests its own WebAPK from its specialized server, while Samsung Internet uses Samsung's trusted provider on Samsung devices. That separation is documented. ([web.dev installation architecture](https://web.dev/learn/pwa/installation), [Chromium architecture](https://chromium.googlesource.com/chromium/src/+/79eb5783e63721b527d40d3ca16d1455af223617/components/webapps/docs/projects/al-site-settings/webapp_android_architecture.md#Installation-Systems))

It does not prove that every future Chrome-generated WebAPK will always satisfy every future Android threshold. As of this research date, Chromium's current WebAPK manifest template declares target API 33. Google's warning rule would make that too old on Android 16/API 36 if the production-minted package uses the same value. The available sources do not expose or guarantee the target SDK of every production WebAPK returned by Google's server. ([Chromium WebAPK AndroidManifest template](https://chromium.googlesource.com/chromium/src/+/refs/heads/main/chrome/android/webapk/shell_apk/AndroidManifest.xml), [Google warning threshold](https://developers.google.com/android/play-protect/warning-dev-guidance#android_app_compatibility_too_low_warning))

So the defensible claim is: **Chrome bypasses the Samsung package pipeline and has been observed to avoid this warning on the same affected device.** “Chrome will always generate a current WebAPK” is not supported by the current primary evidence.

## 4. Can Samsung Internet reliably open Chrome?

Samsung Internet documents the `SamsungBrowser/<version>` token in its user-agent string, so identifying the browser is practical. Since version 24, however, its reduced user agent reports a generic Android platform version. moto can reliably branch on Samsung Internet, but not reliably limit the workaround to only affected Android releases from the user agent. ([Samsung Internet user-agent format](https://developer.samsung.com/internet/user-agent-string-format.html))

An Android web page can offer a user-tapped `intent:` link with Chrome's package (`com.android.chrome`) and an HTTPS URL, for example conceptually:

```text
intent://eltern.moto-app.de/...#Intent;scheme=https;package=com.android.chrome;S.browser_fallback_url=...;end
```

Android/Chrome documents intent links, explicit package targeting, and a fallback URL. It also documents failure cases: no installed handler, no user gesture, and redirects from a typed URL. ([Chrome: Android intents](https://developer.chrome.com/docs/android/intents), [Chrome on Google Play](https://play.google.com/store/apps/details?id=com.android.chrome))

This is therefore a **best-effort button**, not a reliable browser switch:

- Chrome may be absent or disabled.
- Browser and OEM policy can decline or reinterpret `intent:` navigation.
- JavaScript should not auto-launch it; use a real user-tapped link.
- A normal `https:` link is insufficient because Android normally opens the user's default browser, which may remain Samsung Internet. ([Android deep-link routing](https://developer.android.com/training/app-links/create-deeplinks))
- Suppressing moto's own `beforeinstallprompt` use cannot remove Samsung Internet's own “Add to Home screen” menu. The screen must explicitly warn users not to install from that menu while the vendor bug remains.
- Browser storage is isolated. Opening Chrome does not transfer the Samsung Internet login or push subscription, so the user should expect to sign in and enable notifications again.

The UI must therefore include manual fallback instructions such as “Öffnen Sie Google Chrome, rufen Sie eltern.moto-app.de auf und melden Sie sich an,” not only a button that may do nothing.

## 5. Web Push without installation

Installation is not a Web Push prerequisite on Android. Samsung documents Push API and Service Worker support and states that a subscribed user receives notifications whether the web page is currently running or not. This directly covers a closed page/tab. ([Samsung Web Development Guide](https://developer.samsung.com/internet/android/web-developer-guide.html#Web_Push), [Samsung Internet overview](https://developer.samsung.com/internet/android/overview.html#Web_Push))

That makes **uninstalled Web Push in Samsung Internet a viable and smaller workaround** when the functional goal is parent notifications rather than an app icon. It also keeps the existing Samsung Internet session, avoiding a second login and a second browser-specific push subscription.

Limits:

- Samsung's documentation does not promise delivery after the user force-stops/disables the browser, disables browser/site notifications, or when OEM battery policies suppress background work. “Page not running” must not be inflated into an absolute delivery guarantee.
- Notifications belong to Samsung Internet/site permissions and may look less app-like than notifications from an installed WebAPK.
- A launcher icon and standalone task are still missing unless the user adds a shortcut or installs through another supported path.

In the current moto code, Android installation is a **product onboarding gate**, not a platform capability gate: `isPushSupported()` checks Service Worker, PushManager, and Notification APIs, while `ParentNotificationOnboarding` routes every non-standalone Android browser to installation first. Removing that gate for Samsung Internet would need product code and device QA, but no backend push-protocol change is implied. ([push-api.ts](../../frontend/src/lib/push-api.ts), [parent-notification-onboarding.tsx](../../frontend/src/components/parent/parent-notification-onboarding.tsx))

## 6. TWA tradeoffs

A TWA is an Android app shell that opens verified web content fullscreen through a supporting browser. Digital Asset Links prove that the Android app and website have the same owner; failed verification falls back to a Custom Tab. The content is still rendered by the user's browser, and the shell does not directly access browser cookies or local storage. ([Android TWA overview](https://developer.android.com/develop/ui/views/layout/webapps/trusted-web-activities), [Chrome TWA quick start](https://developer.chrome.com/docs/android/trusted-web-activity/quick-start))

Benefits:

- moto owns the Android project and can update its target SDK.
- Distribution through Google Play avoids relying on Samsung's per-site minting output.
- It provides a stable app listing/icon and an app-managed release artifact.
- Web content continues to deploy as web content; only shell/platform changes require an app update.

Costs and caveats:

- Generate and maintain the Android project, signing keys, `assetlinks.json`, Play Console listing, release process, target-API updates, store policy, and Android QA.
- The actual web runtime is still a supporting installed browser. TWA provider selection follows the default supporting browser, then another supporting browser, then falls back to Custom Tabs. ([Chrome TWA provider selection](https://developer.chrome.com/docs/android/trusted-web-activity/quick-start#checking-your-browser))
- Sessions do not automatically migrate from Samsung Internet. A Chrome-backed TWA shares Chrome's profile/storage, not Samsung Internet's. ([Chromium architecture](https://chromium.googlesource.com/chromium/src/+/79eb5783e63721b527d40d3ca16d1455af223617/components/webapps/docs/projects/al-site-settings/webapp_android_architecture.md#Differences-from-Normal-Browser-Usage))
- TWA is operationally disproportionate if the sole requirement is to deliver the existing Web Push notifications.

## Recommended decision for moto

1. **Do not describe this as a defect in moto's web manifest without inspecting the generated package.** The available evidence points to the browser/provider wrapper, but Samsung has not confirmed it.
2. **For the immediate install flow:** detect `SamsungBrowser`, do not invoke its captured install prompt, show a clear warning against Samsung's install menu, and provide both a user-tapped Chrome intent and manual Chrome instructions. Re-test on the reported handset, Android 14, 15, and 16.
3. **Separately challenge the install prerequisite:** if notifications are the reason moto currently forces installation, permit direct Samsung Internet Web Push and test closed-tab, swiped-away browser, reboot, battery-saving, denied permission, and notification-click navigation. This is less work and avoids the failing APK path.
4. **Use a TWA only if app-store presence or ownership of the Android package is a product requirement.** Do not introduce it solely to work around one vendor minting defect.
5. **Re-check SamsungInternet/support #123 before shipping and periodically after:** if Samsung fixes its minting service, the browser-specific block can be removed.
